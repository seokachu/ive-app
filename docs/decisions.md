# 기술 의사결정 기록

포트폴리오/면접 답변용으로 각 선택의 배경과 트레이드오프를 기록한다.

## 1. WebView 하이브리드 vs PWA vs 네이티브 재구현

**선택: Expo + WebView 하이브리드**

- **PWA 대비**: PWA(manifest + 서비스 워커)로도 홈 화면 설치와 웹 푸시가 가능하지만,
  iOS는 사용자가 직접 "홈 화면에 추가"를 해야만 푸시가 동작해 실질 도달률이 낮고,
  앱스토어 입점이 불가능하다. 설치형 앱 경험·스토어 배포 가능성·RN 경험 축적을
  원했기 때문에 하이브리드를 선택했다. (둘은 배타적이지 않아 PWA는 추후 병행 가능)
- **네이티브 재구현 대비**: RN 컴포넌트로 전 화면을 다시 만들면 완성도는 높지만
  작업량이 수 주 단위로 커진다. 이미 완성·배포된 웹(Next.js 16)을 그대로 재사용하는
  것이 비용 대비 효과가 압도적이었다.
- 웹과 앱의 React 버전이 19.2로 정렬되어 있어, 추후 코드 공유(모노레포)로
  확장할 수 있는 여지를 남겼다.

## 2. 별도 리포 vs 모노레포

**선택: 별도 리포 (seokachu/ive-app)**

- WebView 방식은 웹과 공유하는 코드가 거의 없다 (URL과 도메인 목록뿐).
- 웹 리포는 Next 16 + React 19 마이그레이션 직후라, 모노레포 개편으로
  또다시 구조를 흔들 이유가 없었다.
- 네이티브 재구현으로 전환해 코드 공유가 실제로 필요해지는 시점에
  모노레포를 검토하는 것으로 결정을 미뤘다 (YAGNI).

## 3. 푸시 알림에 Firebase(FCM)를 쓰는 이유

**선택: Expo Push + FCM(Android) / APNs(iOS)**

- Firebase를 "선택"한 것이 아니라, **Android 푸시의 공식 전달 채널이 FCM뿐**이다.
  어떤 푸시 서비스를 쓰든 Android 기기로의 최종 전달은 FCM을 거친다.
  iOS의 동일한 역할은 APNs가 한다.
- 전달 구조: 우리 서버 → Expo Push 서버 → FCM/APNs → 기기.
  Expo가 두 플랫폼 채널을 단일 API로 통합해주므로 서버 발송 로직이 단순해진다.
- Firebase의 다른 기능(DB·인증·호스팅)은 사용하지 않는다. 데이터는 계속 Supabase.
- 참고: PWA 웹 푸시를 택해도 Chrome의 푸시 인프라는 FCM이다.

## 4. EAS 클라우드 빌드 vs 로컬 빌드

**선택: 개발 단계는 로컬 빌드(expo run:android), 배포 시 EAS Build**

- 로컬에 Android Studio(SDK + 에뮬레이터)가 이미 있어, 무료로 5~10분 내
  반복 빌드가 가능했다. EAS 무료 플랜의 월 빌드 한도도 아낄 수 있다.
- EAS 프로젝트 연결(projectId)은 푸시 토큰 발급에 필수라 빌드와 무관하게 선행했다.
- 스토어 제출용 서명 빌드는 EAS Build(production 프로필)로 진행 예정 —
  키스토어/인증서 관리를 EAS가 대행해주기 때문.

## 5. 알림 수신자 설계

**선택: 직접 반응 우선 (내 글의 댓글, 내 댓글의 답글)**

- 일반 댓글 → 글 작성자에게, 대댓글 → 글 작성자 + 원댓글 작성자에게.
- 본인이 만든 이벤트는 발송하지 않고, 글 작성자와 원댓글 작성자가 같으면
  더 구체적인 "답글" 알림 하나만 보낸다 (알림 피로 방지).
- 서버 발송 아키텍처 전체와 면접 대비 정리는 웹 리포의
  `docs/push-notifications.md` 참고.

## 6. WebView UX 보강 (앱답게 만들기)

- Android 하드웨어 뒤로가기 → 웹 히스토리 우선 처리 (없으면 앱 종료)
- 인증(Supabase·카카오)·결제(토스) 도메인은 WebView 내부 유지,
  그 외 외부 링크는 시스템 브라우저로 분기 — OAuth/결제 리다이렉트가
  앱 밖으로 새면 흐름이 끊기기 때문
- 오프라인·로드 실패는 `renderError`로 WebView 내장 에러 페이지를 막고 자체 화면으로 대체 —
  내장 페이지는 브랜드와 무관한 데다 재시도 수단도 없어서다. 화면은 웹 404(.pen `오프라인 · 라이트/다크`)의
  디자인 언어를 그대로 쓰고, NetInfo로 연결이 복구되면 자동 reload (앱 v1.0.1)
- iOS WebView 프로세스 종료 자동 복구, 콜드 스타트 시
  푸시 알림의 목적지 URL을 WebView 로드 완료 후 반영
- 메인 히어로의 유튜브 배경 영상은 무음 자동재생이라 WebView 기본값
  (`mediaPlaybackRequiresUserAction=true`)을 풀었다 — 웹에서 되던 것이 앱에서만
  썸네일로 멈춰 있던 원인 (앱 v1.0.2)

## 7. 스플래시 — 네이티브 아이콘 없이 배경색만

**선택: 시스템 스플래시는 배경색만, 로고·타이틀은 RN 오버레이가 한 번에**

- Android 12+ 시스템 스플래시는 "배경색 + 중앙 아이콘"만 허용해 워드마크·태그라인을
  실을 수 없다. 처음엔 아이콘만 먼저 띄우고 RN 오버레이에서 로고+타이틀로 이었는데,
  크기·중심을 dp 단위로 맞춰도(imageWidth 재계산, 태그라인 절대 배치) 사람 눈에는
  로고가 미세하게 어긋나 보였다.
- 그래서 네이티브 단계는 투명 이미지를 넣어 배경색만 보이게 하고, 오버레이의 첫
  `onLayout`에서 `SplashScreen.hideAsync()`를 불러 300ms 페이드로 로고+타이틀이
  한 번에 떠오르게 했다 (`preventAutoHideAsync`로 자동 숨김을 막아 둔 이유).
  `expo-splash-screen` 플러그인은 `image`를 아예 빼면 아이콘 드로어블 참조가 비어
  빌드가 깨지므로 투명 PNG로 우회한다.
- `hideAsync`는 오버레이 첫 레이아웃 · 로드 완료 · 로드 실패 · 15초 안전장치 네 곳에서
  부른다 — 하나라도 빠지면 스플래시에 갇힌다.
- 최소 노출 시간은 두지 않는 게 원칙이지만, 빠른 회선에선 로고가 0.3초 만에 사라져
  깜빡임처럼 보여 **페이드 뒤 1초**만 바닥으로 뒀다. "문구 읽을 시간"이 아니라
  안정감용이라 짧게 잡았고, 로드가 그보다 길면 영향이 없다. 스피너는 10초를 넘길 때만
  붙여 평소엔 브랜드 화면만 보인다. (v1.0.3 ~ v1.0.5)

## 8. App Links 범위와 APK 다운로드 경로

**선택: App Links는 결제 복귀 경로만, APK는 GitHub 릴리스 직결**

- 처음엔 `ive-three.vercel.app` 도메인 전체를 App Links로 잡았다(결제 후 브라우저 대신
  앱으로 복귀). 그러자 앱이 설치된 폰에서 README QR(`/download`)을 찍으면 Chrome이 아니라
  앱 WebView 안에서 열렸고, WebView의 DownloadManager 알림은 눌러도 설치기로 넘어가지
  않아 "다운로드 되었습니다"에서 끝났다. App Links가 없는 다른 앱(vidding-app ·
  energy-meal)은 Chrome이 받아 바로 설치되던 것과의 차이.
- `intentFilters`를 `/payment`, `/mypage/membership/billing` `pathPrefix`로 좁혔고,
  안전장치로 WebView가 `.apk`·GitHub 릴리스 다운로드 URL로 이동하면
  `Linking.openURL`로 시스템 브라우저에 넘긴다. (v1.0.4)
- 웹 `/download`는 한때 동일 출처 스트리밍 프록시(Vercel 함수 → GitHub)를 거쳤는데,
  Range(이어받기) 요청을 처리하지 못해 폰이 네트워크 전환 등으로 끊긴 뒤 실패했다.
  데스크톱·에뮬레이터처럼 안정적인 회선에선 재현되지 않아 찾기 어려웠다. GitHub CDN은
  206/`Accept-Ranges`로 이어받으므로 다른 앱과 같이 직결로 되돌렸다.
- 이름 모를 WebView(카메라 QR 스캐너 등)를 `; wv` 마커로 잡아 `intent://`로 외부
  브라우저를 열던 분기도 제거했다 — 일반 WebView는 intent 스킴을 처리하지 않아
  "여는 중…"에서 멈추고, 그냥 내려받기를 시작하면 대부분 시스템에 다운로드를 넘긴다.
